# Olist 物流延迟与差评分析 说明

## 这个项目在回答什么问题

买家下单时，平台会承诺一个送达日期（比如"23 天内送达"）。实际送达可能提前、可能推后。我想看的是：

**物流有没有准时送，是不是买家打差评的关键原因？延迟的订单差评率是不是明显更高？**

## 用的数据

PostgreSQL 里的 `olist` 库，主要两张表：

- `orders`：每笔订单，含下单时间、实际送达时间、承诺送达时间、订单状态
- `reviews`：每笔订单的评分（1-5 星），一个订单可能有多条评论

## 这段代码是怎么写的（对应 olist_analysis.sql）

代码用 `WITH` 先搭了几张中间表，最后一次性算出核心结果。

### 1. 订单表（CTE）

算每笔已送达订单的延迟天数：

```
延迟天数 = 实际送达日期 - 承诺日期
```

正数 = 晚到，负数 = 提前，0 = 准时。只保留订单状态为 delivered 的。

用 `::date` 把时间戳转成日期再相减，得到整数天（和 pandas 里 `.dt.days` 一个口径）。

### 2. 平均表（CTE）

在上面的订单表基础上，算整体统计：

- 平均配送天数
- 平均承诺天数
- 延迟率（延迟订单占比）

算出来：平均配送 12.5 天、平均承诺 24.4 天、延迟率 6.77%。

这里能看到一个现象：承诺 24 天、实际 12 天就到——平台承诺得保守，多数订单其实提前到。

### 3. 均分表（CTE）

把 reviews 按订单号聚合，取每单的平均评分。

关键：一个订单可能有多条评论，所以 `GROUP BY order_id` 取平均分，这样每单只有一条评分，后面关联才不会让行数膨胀。

### 4. 总表（CTE）

把订单和评分按订单号关联（LEFT JOIN），并加一列"是否延迟"：

```
延迟天数 > 0 → '延迟'，否则 '准时'
```

到这里，每单一行：订单号 + 平均评分 + 延迟天数 + 是否延迟。

### 5. 主查询

按"是否延迟"分两组，统计：

- 差评数：评分 ≤ 2 的订单数（1-2 星算差评，3 星算中性）
- 差评率：差评数 ÷ 该组订单数

## 结论

```
延迟组差评率 62.4%   准时组差评率 9.2%
```

延迟的订单，差评率是准时的近 7 倍。

**物流延迟就是差评的关键驱动。** 平台承诺得保守，多数订单提前到（惊喜），所以整体差评率不高（9% 左右）；但一旦超过承诺日期（破预期），差评率就断崖式跳到 62%。

## 和其他方法的印证

这个结论和用 Python + 随机森林做出来的结果一致：

- 随机森林里，延迟天数的特征重要性 0.887，排第一（最能解释差评）
- SQL 分组算出的差评率对比（62.4% vs 9.2%）也是同一个方向

两条独立的方法（SQL 分组 + 机器学习）指向同一个结论：延迟是差评的核心驱动力。
