# Olist 巴西电商经营分析：物流履约 × 商品市场 × 经营底座

> 基于 Olist 巴西电商公开数据集（约 9.5 万订单、27 州、9 张表）的经营质量诊断：
> **一个数据集、一套方法论、三个分析层**——物流侧回答"货怎么送到"，商品侧回答"货怎么卖"，经营底座回答"这盘生意多大、钱怎么转"。
> 工具链：Python (pandas / scikit-learn) · Power BI · SQL

> **原始数据说明（首次运行前必读）**：本仓库不含原始数据（9 个 CSV 共约 121MB，其中地理坐标表 61MB，未随包分发）。请到 Kaggle 下载后放入 `data/raw/`，具体步骤见 [`data/raw/README.md`](data/raw/README.md)。
> 下载地址：https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce
> **只看结果无需下载**：`logistics/data/`、`market/data/`、`metrics/out/` 的结果表与全部图表已随包提供，可直接查看；要复现分析过程才需要原始数据。

## 一、项目概览

本项目从三个分析层描述同一个平台：配送能否兑现承诺、商品能否卖对市场、这盘生意本身的规模与结构。同一份订单数据、同一套诊断方法。

| | 方向一：物流履约（供应链侧） | 方向二：商品市场（经营侧） | 经营底座（metrics/） |
|---|---|---|---|
| 回答的问题 | 延迟从哪来、该怎么治 | 卖什么、卖多少钱、在哪卖 | 生意多大、钱怎么转、什么动作无效 |
| 分析单位 | 订单 → 线路（37 条主要线路） | 订单 → 商品行（110,197 件） | 订单 / 客户 / 卖家 / 月（20 个完整月） |
| 核心产出 | 承诺校准方案 + 前置仓选址 | 品类结构 + 价格带 + 区域市场分层 | 21 项经营指标 + 月度经营表 + cohort 留存 |
| 服务决策 | 物流 / 供应链 | GTM / 商品 / 市场 | 预算分配 / 增长策略 / 定价与履约投入 |

**三层不是三份独立分析**：共用同一底座口径（delivered 订单、订单平均评分、差评=均分≤2、件数口径、分箱逻辑一致），共用同一套方法（异常定位 → 根因量化 → 方案验证），并在结论上互相印证——

> **里约热内卢（RJ）在两个方向上同时异常**：物流方向，圣保罗→里约是最大异常线路（延迟率 14.25%，超额延迟订单数 624，断层第一）；商品方向，里约买家的全品类差评率 20.81%，27 州中最差。

## 二、核心发现（数字钉实）

**方向一：物流履约**

| 发现 | 数据 |
|---|---|
| 最大异常线路 | **SP→RJ**（圣保罗→里约，8,021 单） |
| 该线延迟率 | **14.25%**，是同距离档（200-500km）正常水平 6.47% 的 **2.2 倍** |
| 超额延迟订单数 | **624 单**，为第二名的 **8.4 倍**（断层第一） |
| 距离是否背锅 | 官方公路仅 **429km**（买卖双方球面中位距离 383km）——问题不在距离，在配送执行 |
| 承诺错配 | 里约现状承诺 26 天、实际需要 37 天，**缺 11 天** |
| 方案效果 | 校准后订单数 ≥500 的 27 条线路延迟率全部压到 **6.4% 以内**（SPRJ 14.25%→5.98%） |
| 归因结论 | 随机森林：延迟天数权重 **0.883**、承诺天数 0.117——**延迟是差评的第一驱动** |

**方向二：商品市场**

| 发现 | 数据 |
|---|---|
| 品类口碑差 | 74 个品类，件数加权差评率 **14.73%**，均分 4.08 |
| 问题品类（量大且口碑差） | 床品家纺 10,831 件 / 差评率 **18.08%**；家具装饰 17.97%；电脑配件 17.00% |
| 机会品类（量大且口碑好） | 美妆健康 9,402 件 / 差评率 **12.45%** |
| 主力价格档 | **50-100 元**（32,492 件，占 29.5%），差评率 15.18% |
| 价格与口碑 | 价格对口碑影响弱（各档 14.2%~16.2%）——**问题不在价格带，在商品与履约质量** |
| 区域市场分层 | 圣保罗 46,448 件 / 差评率 **12.40%**（全国最好）；里约 14,143 件 / **20.81%**（全国最差）；巴伊亚 18.83% |
| 差评文本主题 | 差评第一痛点是物流（提及率 34.5%，好评仅 15.6%）；售后/客服提及率为好评的 **7 倍**——出问题后的处理是第二短板 |
| 3C 竞争位 | 手机中位价仅 30 元（全平台 74.9 元）——平台 3C 是低价配件市场；电脑配件差评率 17.00% 为 3C 内最高 |
| 订单全链路 | 下单→签收转化 **97.02%**（99,441 单中 96,476 单签收）；链路 11.5 天里 **8.9 天（77%）在末端配送**；最大流失点在"批准→交承运商"（1,623 单） |
| 用户复购与分层 | 复购率仅 **3.12%**（典型的拉新驱动生意）；但复购客户人均消费是一次性客户的 1.8~3.1 倍，三次及以上客户人均 420.91 元、差评占比最低（10.89%） |
| 品类 × 履约联合 | 差评率 14.73% 里 **3.33 个百分点（22.6%）与延迟同现**；品类口碑差距主要来自品类自身（准时组差评率 6.4%~22.3%） |
| 物流杠杆最大的品类 | 文具 **32.4%**、美妆健康 **32.1%**、玩具 29.6% 的差评与延迟同现；办公家具只有 12.6%（品类自身问题） |
| 区域品类渗透（模块十） | 前 8 州 × 21 品类 = 168 格覆盖 76.3%；办公家具在巴伊亚指数 **1.667**、里约 **1.425**（该格差评率 38.54%），联邦区仅 **0.509**——同一品类跨州差三倍 |
| 品类级产品痛点（模块十一） | 产品类提及率（扩展词典）最高：钟表礼品 22.8%、电脑配件 22.7%、手机通讯 22.6%；最低：工具园艺 11.5%、游戏机 12.5%。办公家具 **15.0%** 的差评提到缺件/少发 |
| 词典交叉检验 | 120 条抽检：原词典两类完全一致率 65.8%、产品类漏配 24 条；补词后 **79.2%**、漏配降到 14 条——产品类提及率是**下界**，只作品类间相对比较 |
| 州际价差来源（模块十二） | 价格效应仅 **−0.40~+5.13 元**、结构效应占 **86.6%~101.4%**——差异来自买的款式不同，不是同款定价不同；运费差 +2.91~+8.45 元 |

**经营底座（`metrics/`）**

| 发现 | 数据 |
|---|---|
| 规模与客单结构 | GMV **1,568 万** BRL（商品 1,345 万 + 运费 219 万），97,910 有效订单，AOV **160.18** = 商品 137.37 + 运费 22.82 |
| 连带率决定天花板 | 连带率 **1.14**、**90.06%** 订单只买一件 → 凑单满减、关联推荐、搭售在这盘生意里天花板极低，提客单只能靠提价或品类升级 |
| 运费在吃毛利 | 运费率 **16.61%**，前 10 个月 15.92% → 后 10 个月 16.94%（2017 年 16.08% → 2018 年 17.06%），同期 AOV 161.4 → 159.6 基本不动；免邮订单仅 **0.35%**（343 单）→ 包邮是结构性变革，不是运营可选动作 |
| 增长靠拉新 | 复购率 **3.04%**、2018 年新客占 **97.63%**、cohort 次月留存中位 **0.51%**（留存曲线贴底是结论，不是算错） |
| 复购周期高度分散 | 回购间隔中位 **71 天**、P25–P75 = **23–170 天**；30 天内复购仅 **29.7%** → 不存在统一的召回窗口 |
| 同日拆单会假造复购 | 2,875 个"复购客户"里 **845 人（29.4%）** 首末单在同一天。含进去算，间隔中位假到 34 天、"30 天内回来"假到 48.7%；剔除后是 71 天 / 29.7% |
| 分期是本地化习惯 | 分期渗透 **51.49%**，分期订单中 2–5 期占 **68.6%**、12 期以上仅 0.32% → 巴西买家看月供不看总价 |
| 供给端极度分散 | 3,029 家卖家、Top10 仅 **13.24%**、HHI **36**（与亚马逊头部主导相反） |

## 三、方向一：物流履约（`logistics/`）

**问题**：延迟率随距离上升是常识，但巴西平台的延迟集中在少数线路——这些线路的延迟是距离造成的，还是执行造成的？

**方法**：构建"订单 → 线路"两级分析框架（37 条主要线路），用距离分档建立基准线，识别超额延迟线路；把"超额延迟订单数 = 订单数 ×（线路延迟率 − 同档基准）"作为问题优先级排序依据；再用随机森林做差评归因，最后验证承诺校准方案。

**关键过程**：距离分档基准 0-200km 4.59% → 2000km+ 12.13%；跨州 8.13% vs 州内 4.55%（1.8 倍）；但 SPRJ 在 383km 档上出现 14.25% 的极端离群（同档仅 6.47%）——离群点定位后，误差来源被锁定为承诺天数与实际所需天数的错配。

**产出**：
- `logistics/报告_物流履约.md` 分析报告全文
- `方法与口径.md`（仓库根）全项目口径决策、方向差异说明与高频问答
- `logistics/data/` 37 条主要线路结果表、距离分档、州内跨州
- `logistics/图表/` 10 张图（6 张分析图 + 4 张 Power BI 看板截图）

## 四、方向二：商品市场（`market/`）

**问题**：平台卖什么品类口碑好、什么品类在拖后腿？价格带与口碑有没有关系？哪些市场值得投入、哪些需要治理？

**方法**：以商品行为分析单位（一单多品类则分别计入各品类），把订单评分聚合到商品行；十二个模块依次回答：品类结构（卖什么）、价格带（卖多少钱）、区域市场（在哪卖）、品类×履约联合（口碑差是配送还是品类自身）、销量预测（趋势外推）、差评文本主题（用户不满什么）、3C 竞争位（平台内定位）、订单全链路漏斗（链路转化与耗时）、用户复购与分层（客户价值）、品类×州渗透指数（哪个州哪个品类超配）、品类级产品痛点（每个品类具体被骂什么）、价格带结构分解（州际价差来自款式组合还是同款定价）。价格带边界用分布拐点 + 业务整数（0/20/50/100/200）确定，并用第二套边界（0/30/60/120/240）做敏感性检验。

**关键过程**：品类件数加权差评率 14.73%，其中床品家纺（18.08%）、家具装饰（17.97%）为问题品类，美妆健康（12.45%）为机会品类；价格带主力档 50-100 元占 29.5%，口碑最好档 100-200 元（14.17%），价格对口碑影响弱，说明口碑主要受品类属性与履约影响；区域上圣保罗最好（12.40%）、里约最差（20.81%）——与物流方向的里约异常互为证据。

**产出**：
- `market/报告_商品市场.md` 分析报告全文
- `market/analysis.py` 数据层（底座 + 模块①-⑫：品类/价格带/区域/履约联合/销量预测/差评文本/3C/订单漏斗/用户复购/品类×州渗透/品类级痛点/价格带分解）
- `market/charts.py` 展现层（16 张图，含品类 × 履约联合 3 张与整页汇总）
- `market/品类履约联合_交互看板.html` 单文件交互看板（零依赖、离线可用、双击即开）
- `market/data/` 21 张结果表（品类结构、价格带、区域画像、区域品类、品类履约联合、品类销量预测、差评主题、3C品类竞争位、订单漏斗、用户复购分层、品类产品痛点、品类差评特有词、品类州价格带、价格分解、同SKU跨州定价、文本标注抽检、文本标注一致率等）
- `market/图表/` 16 张图（品类定位/价格带/区域市场/区域品类偏好、履约联合 3 张、品类 × 州 2 张、品类产品痛点、价格分解、预测/文本/3C/漏斗/复购 各 1 张）+ 1 张 Power BI 看板页截图（`看板_品类履约.png`）

**延伸：品类 × 履约（`analysis.py` 模块④ + `charts.py`）**——把方向一的订单级延迟标记接到本方向的商品行上，回答"口碑差的品类，是配送慢连累的，还是品类自身的问题"：平台层延迟贡献 **3.33 个百分点（占差评 22.6%）**，品类层在 12.6%~32.4% 之间，结论见 `报告_商品市场.md` 5.2，口径见根目录 `方法与口径.md` 3.7。

## 五、经营底座（`metrics/`）

**问题**：前两层回答"哪里出了问题"，但所有"改善 X%"的建议都需要一个分母——这盘生意多大、客单价是怎么构成的、钱从哪进、留存到底有没有空间、供给端是谁在供货。

**方法**：以订单级金额表为底（商品行聚合到订单，剔除 canceled / unavailable），在 **20 个完整月（2017-01 ~ 2018-08）** 的窗口内重算 21 项经营指标，分六组：规模与价格（GMV / AOV / 件单价 / 连带率）、运费（运费率 / 免邮占比）、支付（分期渗透 / 期数分布 / 信用卡占比）、客户（复购率 / 回购间隔 / cohort 留存 / 新客占比）、卖家（数量 / Top10 份额 / HHI）、订单质量（取消率 / 不可用率 / 评分）。

**为什么单独设一个窗口**：2016 年只有 329 单、2018-09 之后只有 20 单，首尾是不完整期。所以本层口径是 **97,910 单**，与方向一（94,702 单，需完整物流时间戳）、方向二（99,441 单全量）不同。**三个口径并存是设计，不是错误**——但引用数字时必须说清是哪一层，不能跨层比较。

**关键过程**：

- 客单价 160.18 拆成 137.37（商品）+ 22.82（运费），商品部分再拆成件单价 120.35 × 连带率 1.14 —— 由此才能判断"客单价涨了，是卖贵了还是买多了"。
- 运费率 16.61%，前 10 个月 15.92% → 后 10 个月 16.94%，同期 AOV 从 161.4 掉到 159.6：**两年没提价，运费在吃毛利**。
- 复购率 3.04%，但 2,875 个"复购客户"里有 845 人（29.4%）首末单在同一天——同日拆单是同一笔消费拆成两单，不是复购。**剔除后回购间隔中位 71 天（P25–P75 = 23–170 天）、30 天内复购仅 29.7%**，含进去会假到 34 天 / 48.7%。

**产出**：
- `metrics/指标口径.md` 21 项指标的公式、分母、坑与本期值
- `metrics/metrics.py` 计算脚本（输出 6 张结果表）
- `metrics/build_dashboard.py` + `metrics/dashboard/经营总览.html` 单文件经营看板（离线可用）
- `metrics/out/` 指标总表、月度经营表（20 行 × 19 列）、cohort 留存矩阵、分期期数分布、支付结构、卖家 Top50

## 九、运行说明（复现路径）

```bash
# 1. 从 Kaggle 下载 Olist 数据集，解压后把 9 个 CSV 放进 data/raw/
# 2. 安装依赖
pip install -r requirements.txt

# 3. 方向一：物流履约
python logistics/analysis.py
#    输出：logistics/data/分线路统计.csv、距离档.csv、州内跨州.csv

# 4. 方向二：商品市场
python market/analysis.py
python market/charts.py
#    输出：market/data/ 21 张结果表（底座 商品主表 + 模块①-⑫ 的结果表；模块⑩-⑫ 新增 品类产品痛点、品类差评特有词、品类州价格带、价格分解、同SKU跨州定价、文本标注抽检、文本标注一致率）
#         + market/图表/ 16 张图 + 交互看板 HTML + Power BI 导入表（品类履约联合_PowerBI.csv）
#    注：文本标注抽检.csv 的"人工/AI复核主题"列是逐条复核结果（比对见 方法与口径.md 3.14），
#        重跑 analysis.py 不会覆盖该表（脚本检测到已存在即跳过），一致率表由该列与规则列比对得出

# 5. 经营底座：21 项经营指标（20 个完整月窗口）
python metrics/metrics.py
python metrics/build_dashboard.py
#    输出：metrics/out/ 指标总表.csv、月度经营表.csv、cohort_留存矩阵.csv、分期期数分布.csv、支付结构.csv、卖家Top50.csv
#         + metrics/dashboard/经营总览.html

# 6. 看板：用 Power BI Desktop 导入 logistics/data/ 与 market/data/ 的结果表搭建
#    物流 6 页截图见 logistics/图表/07-10；品类×履约页见 market/图表/看板_品类履约.png（源文件 123.pbix）
```

> 仓库内 `logistics/data/`、`market/data/`、`metrics/out/` 已含运行结果，不跑代码也可直接查看。
> Mac/Linux 若图内中文显示为方块，安装 Noto Sans CJK 字体即可（Windows 自带微软雅黑，无需处理）。

## 十、技术栈

- **Python**：pandas 数据清洗与聚合、scikit-learn 随机森林（特征重要性归因）、分箱与敏感性检验、matplotlib 制图（代码使用中文列名与中文业务场景一致）
- **Power BI**：7 页交互看板（物流 6 页：问题严重度 / 延迟规律与里约反例 / 方案效果等；品类×履约 1 页：切片器联动 + 交叉筛选）
- **SQL**：Olist 数据查询与口径验证（差评率分组统计、延迟率多口径交叉核对，与 Python 结果相互验证）

> 仓库内每个引用数字均可由 `logistics/analysis.py`、`market/analysis.py` + `data/` 结果复现；如对任何数字有疑问，可用代码验证。
